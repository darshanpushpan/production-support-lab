# Title: Alerts, and fixing the dashboard that stayed green
Date: 2026-10-26

## What I did
Fixed the two things the last post ended on, then added alerting.
- Moved orders_pending and orders_oldest_pending_seconds from the worker to the API. The API reads them straight from Postgres every time Prometheus scrapes it, so they keep working when the worker is dead.
- Stat panels now show NO DATA in orange instead of a green "no data".
- 6 alert rules: WorkerDown, ApiDown, OrdersBacklog (oldest pending over 30s), OrdersLost (over 10 min), OrdersErrorRate, OrdersSlow. Checked with promtool and amtool before starting anything.
- Alertmanager sends alerts to a small Python receiver that logs one line per alert. That receiver is where the ServiceNow bridge will go.
- Wrote docs/runbooks/worker-down.md, linked from the WorkerDown alert.

## What broke or surprised me
1. The first alert fired about a minute after I switched alerting on, and it was real. OrdersLost: "An order has been pending for 6d 14h 59m". When I shut Docker down on Oct 20 the worker was still working through the 3014 order backlog, so some orders sat there for 6 and a half days. Nothing told me until now.
2. One problem, two alerts. OrdersBacklog (warning) fired a minute after OrdersLost (critical) for the same stuck orders.
3. The RESOLVED message for OrdersLost still said "pending for 6d 14h 44m". Alertmanager sends the last value from while it was firing, not the current value. Need to keep that in mind when these become tickets.

## What I tried (including what didn't work)
Added an inhibit rule: if OrdersLost or WorkerDown is firing, OrdersBacklog is suppressed. Then stopped the worker again:
- 19:38:34 worker stopped
- 19:40:09 WorkerDown fired (1m35s: 15s scrape interval + 1m for + 10s group wait)
- 19:41:43 OrdersBacklog firing in Prometheus but suppressed in Alertmanager, so only one alert reached the receiver
- orders_pending from the API showed 125 while the worker was down (before this change it showed no data)
- 19:42:13 worker started, 19:43:09 WorkerDown resolved

## Decision and why
- for: 1m on WorkerDown instead of firing on the first failed scrape. One missed scrape shouldn't page anyone, and 1m35s to detect is fine for this system.
- OrdersBacklog exists because SLO 3 only counts orders that finish. Stuck orders never show up in it, so the queue needs its own alert.
- Inhibit the warning when a critical alert about the same problem is already firing.
